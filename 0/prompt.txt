/authorized-security-audit # Advanced Security Assessment — Psychology Clinic Platform

Act as a senior Application Security Engineer, Web Penetration Tester, Python Security Auditor, and Defensive Security Consultant.

Use the globally installed `authorized-security-audit` skill and HackingTool 3.1.0 through WSL Ubuntu 24.04.

## 1. Project Scope

Repository:
https://github.com/sepantasaadat/psychology_bot

Use the currently open local workspace as the primary source of truth. Do not clone another copy or assume the public GitHub version is identical to the local working tree.

This project is a psychology clinic management platform consisting of:

- Flask web application.
- Telegram bot built with python-telegram-bot.
- SQLite database.
- Appointment booking and cancellation workflows.
- Administrator dashboard and authorization.
- Payment receipt image uploads.
- Image validation and processing using Pillow.
- Telegram notifications and administrator actions.
- SMTP email notifications and scheduled appointment reports.
- Configuration and secrets management.

## 2. Security Assessment Objectives

Conduct a comprehensive, evidence-based assessment of the entire application.

### A. Web Application Security

Evaluate:

- Authentication and session management.
- Authorization and role-based access control.
- Administrator endpoints.
- Insecure Direct Object References (IDOR).
- Cross-Site Request Forgery (CSRF).
- Cross-Site Scripting (XSS).
- SQL injection and database query construction.
- Server-Side Request Forgery (SSRF), where applicable.
- HTTP security headers.
- Cookie security flags.
- Flask secret key management.
- Debug mode and production configuration.
- Input validation and output encoding.
- Request size limits and rate limiting.
- Error handling and sensitive information disclosure.
- Production server configuration and reverse proxy trust.

Pay particular attention to appointment creation, approval, rejection, cancellation, and access to administrative functionality.

### B. Telegram Bot Security

Inspect `main.py` and all related bot components.

Evaluate:

- Telegram BOT_TOKEN storage and exposure.
- Administrator identity verification.
- Unauthorized callback execution.
- Callback data manipulation.
- Privilege escalation.
- User-to-appointment ownership verification.
- Unauthorized appointment modification or deletion.
- Race conditions in appointment booking.
- Duplicate callback handling.
- Rate limiting and Telegram API abuse.
- Sensitive information in logs and Telegram notifications.
- Long polling and webhook security, where applicable.

Verify that every sensitive administrative operation has server-side authorization checks.

### C. Receipt Upload Security

Pay special attention to `security.py` and the receipt processing pipeline.

Evaluate:

- File type verification using actual file content.
- MIME type validation.
- Filename and path traversal protection.
- Image decompression bombs.
- Malformed images and parser vulnerabilities.
- EXIF and metadata handling.
- Temporary file management.
- Private storage permissions.
- Unauthorized receipt retrieval.
- File overwrite and collision risks.
- Upload size restrictions.
- Safe error handling.

Do not assume the existing Pillow re-encoding mechanism is completely secure without validating its implementation.

### D. SQLite and Database Security

Inspect `database.py` and all database interactions.

Evaluate:

- SQL parameterization.
- Database file permissions.
- Transaction handling.
- Appointment ownership and isolation.
- Concurrent booking and double-booking conditions.
- Database backup security.
- Sensitive data retention.
- Data exposure through administrative queries.
- Database integrity and failure recovery.

Never inspect or export actual patient records, appointment histories, or production database contents.

Use synthetic records for any required tests.

### E. SMTP and Notification Security

Inspect `daily_report.py`, `config.py`, and all notification code.

Evaluate:

- SMTP credential handling.
- TLS configuration and certificate verification.
- Email HTML injection.
- Sensitive information included in outgoing reports.
- Telegram notification exposure.
- Request timeouts and retry handling.
- Secret leakage through exception messages and logs.
- Email recipient restrictions.

Do not send actual emails or Telegram messages during testing.

Do not call external notification APIs.

### F. Secrets and Repository Security

Inspect:

- `.env` handling.
- `.gitignore`.
- `config.py`.
- Git commit history.
- Python dependency manifests.
- Hardcoded credentials.
- Default production secrets.
- Exposed API keys and authentication tokens.

Search for leaked secrets without displaying their actual values.

Redact all potentially sensitive information in reports.

Identify secrets in Git history separately from secrets present in current source files.

Do not rewrite Git history or revoke credentials automatically.

### G. Dependency and Deployment Security

Review:

- `requirements.txt`.
- Installed Python dependencies.
- Known vulnerable packages.
- Dependency compatibility.
- Flask and Werkzeug security.
- Pillow security.
- python-telegram-bot security.
- Gunicorn configuration.
- systemd service permissions.
- Linux file permissions.
- Production environment configuration.
- Backup and deployment practices.

Do not install or upgrade dependencies without my explicit approval.

Do not scan:

- The production VPS.

- GitHub infrastructure.
- Third-party services.

This application handles potentially sensitive psychological clinic information.

Treat the following as confidential:

- Patient names.
- Telephone numbers.
- Appointment schedules.
- Session types.
- Payment receipts.
- Administrator identifiers.
- Clinic operational information.

Evaluate data minimization, access restrictions, retention, logging, backups, and secure transmission.

Never display real patient records in the final report.

Use synthetic test information only.

Clearly identify any privacy or data-protection risks that may require additional legal or regulatory assessment.

Do not claim regulatory compliance without sufficient evidence.

یافته SEC-04: فقدان هدرهای امنیتی HTTP و پرچمهای امنیتی کوکی
شدت: Medium
فایل و خطوط: app.py
تحلیل فنی: پاسخهای ارسالی از سمت سرور وب فاقد هدرهای امنیتی مدرن هستند:
X-Content-Type-Options: nosniff: جلوگیری از تفسیر نادرست فرمت فایل توسط مرورگر.
X-Frame-Options: SAMEORIGIN یا Content-Security-Policy: frame-ancestors: جلوگیری از حملات Clickjacking.
Strict-Transport-Security (HSTS): اجبار به استفاده از کانال امن HTTPS. همچنین پرچمهای کوکی نظیر SESSION_COOKIE_SECURE و SESSION_COOKIE_HTTPONLY و SESSION_COOKIE_SAMESITE به صراحت فعال نشدهاند.
راهکار اصلاحی: استفاده از هوک after_request برای تزریق هدرها: python
@app.after_request
def set_security_headers(response):
response.headers['X-Content-Type-Options'] = 'nosniff'
response.headers['X-Frame-Options'] = 'SAMEORIGIN'
response.headers['Referrer-Policy'] = 'strict-origin-when-cross-origin'
return response

۷. ارزیابی حریم خصوصی و دادههای سلامت (Privacy & Healthcare Data)
این سامانه به عنوان درگاه رزرو کلینیک روانشناسی، اطلاعات سلامت فردی (PHI) را مدیریت میکند. ارزیابی ابعاد محرمانگی:
دادههای در حال انتقال (In Transit): در لایه تلگرام، ارتباطات از طریق سرورهای ابری تلگرام منتقل میشوند و به عنوان کانال خارج از کنترل مستقل کلینیک در نظر گرفته میشوند. در لایه وب، وابستگی کامل به پیکربندی TLS در وبسرور میزبان (Nginx/Reverse Proxy) وجود دارد و باید پروتکل HTTPS اجباری باشد.
دادههای در حالت سکون (At Rest): پایگاه داده SQLite به صورت پیشفرض رمزنگاریشده نیست. دسترسی فیزیکی یا غیرمجاز به فایل clinic.db روی سرور منجر به افشای هویت، شماره تماس و زمان جلسات مشاوره مراجعین خواهد شد.
لاگها و فایلهای لاگگیری: بررسی کدهای main.py و app.py نشان داد که نام و شماره تلفن مراجعین در متن لاگها ثبت نمیشود و لاگرهای خارجی (werkzeug و httpx) به سطح اخطار محدود شدهاند که از نشت ناخواسته اطلاعات در ژورنال لینوکس جلوگیری میکند.
